# Descripciones textuales de casos de uso — Módulo B (Tutor)

## CU-TUT-01 — Registrarse como tutor (HU-002)

1. **ID:** CU-TUT-01  
2. **Actor:** Tutor no registrado; Administrador como actor secundario de aprobación.  
3. **Propósito:** Solicitar una cuenta para ofrecer tutorías.  
4. **Resumen:** El tutor completa datos personales/profesionales, adjunta fotografía y envía la solicitud.  
5. **Precondiciones:** Correo, carnet e identificación no existen; la API y MySQL están disponibles.  
6. **Flujo normal:** (1) abre registro, (2) ingresa datos y contraseña, (3) adjunta JPG/PNG/WEBP de hasta 5 MB, (4) el sistema valida, hashea con bcrypt, guarda perfil y asocia la materia, (5) responde solicitud pendiente.  
7. **Alternativas:** Puede seleccionar `OTHER` o `UNSPECIFIED` en género; el catálogo reutiliza una materia existente con el mismo nombre.  
8. **Excepciones:** Campos faltantes, correo inválido, contraseña débil, fecha/año inválidos, foto ausente o duplicados devuelven 400/409 y limpian el archivo temporal.  
9. **Postcondiciones:** `users.status = PENDING`, perfil creado y contraseña nunca visible en claro.  
10. **Reglas:** Foto obligatoria; contraseña de mínimo 8 caracteres con mayúscula, minúscula y número.  
11. **Extensiones:** CU-ADM-02 puede aprobar o rechazar la solicitud.

## CU-TUT-02 — Iniciar sesión como tutor (HU-007)

1. **ID:** CU-TUT-02  
2. **Actor:** Tutor registrado.  
3. **Propósito:** Acceder a horarios, perfil y sesiones.  
4. **Resumen:** La API compara correo/contraseña y verifica el estado administrativo.  
5. **Precondiciones:** Existe perfil tutor asociado; la cuenta fue aprobada.  
6. **Flujo normal:** (1) ingresa correo y contraseña, (2) backend consulta rol tutor, (3) compara bcrypt, (4) verifica `APPROVED`, (5) emite JWT de 8 horas.  
7. **Alternativas:** El enlace “Regístrate como tutor” lleva a `/register`.  
8. **Excepciones:** Datos incorrectos → 401; `PENDING`, `REJECTED` o `DISABLED` → 403 con mensaje específico.  
9. **Postcondiciones:** Token guardado por el cliente y enviado como Bearer en rutas privadas.  
10. **Reglas:** No se permite acceso por conocer únicamente el correo; el rol debe ser `tutor`.  
11. **Extensiones:** El JWT habilita CU-TUT-03, CU-TUT-04 y CU-TUT-05.

## CU-TUT-03 — Establecer disponibilidad (HU-008)

1. **ID:** CU-TUT-03  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Publicar los días y horas en que atiende.  
4. **Resumen:** Selecciona uno o más días y un rango común de inicio/fin.  
5. **Precondiciones:** JWT válido con `role=tutor`; perfil existente.  
6. **Flujo normal:** (1) marca días, (2) define horas, (3) cliente valida, (4) `POST /api/tutors/me/schedules` reemplaza la disponibilidad activa en una transacción, (5) confirma guardado.  
7. **Alternativas:** Puede consultar el horario actual con `GET /api/tutors/me/schedules`.  
8. **Excepciones:** Ningún día, hora inválida o inicio mayor/igual al fin → 400.  
9. **Postcondiciones:** Cada día queda asociado al mismo rango en `schedules` y puede consultarse públicamente.  
10. **Reglas:** Días ISO 1–7; `start_time < end_time`; máximo una fila activa por tutor y día.  
11. **Extensiones:** CU-TUT-04 permite modificar posteriormente el horario.

## CU-TUT-04 — Actualizar disponibilidad (HU-019)

1. **ID:** CU-TUT-04  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Adaptar días y rango sin dejar sesiones pendientes fuera de agenda.  
4. **Resumen:** El tutor edita el formulario y el backend verifica conflictos antes de guardar.  
5. **Precondiciones:** Horario existente, JWT válido y sesiones `PENDING` consultables.  
6. **Flujo normal:** (1) carga horario, (2) modifica días/rango, (3) `PUT /api/tutors/me/schedules` bloquea filas, (4) comprueba cada sesión pendiente, (5) actualiza filas y confirma.  
7. **Alternativas:** Si no hay conflictos se reemplazan días y se conservan las sesiones.  
8. **Excepciones:** Una sesión cae en día no seleccionado o fuera del rango → 409 y rollback completo.  
9. **Postcondiciones:** Horario actualizado o sin cambios si hubo conflicto.  
10. **Reglas:** La comparación de intervalos es inclusiva por contención: la sesión debe quedar dentro del rango nuevo.  
11. **Extensiones:** HU-014 consume las sesiones pendientes que protegen esta actualización.

## CU-TUT-05 — Consultar y actualizar perfil (HU-023)

1. **ID:** CU-TUT-05  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Mantener vigente la información personal y profesional.  
4. **Resumen:** Consulta su perfil y modifica datos salvo el correo.  
5. **Precondiciones:** JWT válido y perfil asociado.  
6. **Flujo normal:** (1) `GET /api/tutors/me/profile`, (2) muestra correo de solo lectura, (3) edita campos permitidos, (4) `PUT` valida y guarda, (5) confirma actualización.  
7. **Alternativas:** Puede enviar una nueva contraseña opcional; se valida y almacena con bcrypt.  
8. **Excepciones:** Intento de cambiar correo → 400; contraseña débil → 400; carnet/identificación duplicados → 409.  
9. **Postcondiciones:** Perfil actualizado; correo y contraseña mantienen sus reglas de seguridad.  
10. **Reglas:** Todos los datos del perfil son obligatorios; el correo es inmutable.  
11. **Extensiones:** El cambio se refleja en el listado público de tutores aprobados.

## CU-TUT-06 — Atender Estudiante y Registrar Resumen (HU-028)

1. **ID:** CU-TUT-06  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Registrar la finalización de una sesión y asentar la retroalimentación.  
4. **Resumen:** El tutor marca una cita pendiente como atendida completando un resumen obligatorio.  
5. **Precondiciones:** JWT válido; el tutor tiene al menos una sesión asignada en estado `PENDING`.  
6. **Flujo normal:** (1) `GET /api/tutors/me/sessions` consulta sesiones pendientes, (2) selecciona la cita, (3) redacta el resumen académico, (4) `PUT /api/sessions/{id}/attend` valida el body, (5) *<<include>>* el sistema asocia el resumen y cambia el estado, (6) responde 200 OK.  
7. **Alternativas:** Si cierra el modal sin enviar, la sesión permanece en estado `PENDING`.  
8. **Excepciones:** Body sin el campo `summary` o con texto vacío → 400 (Bad Request).  
9. **Postcondiciones:** El registro en base de datos cambia a `ATTENDED` (o `COMPLETED`), eliminándose de la bandeja de pendientes del tutor.  
10. **Reglas:** La inclusión del resumen es estrictamente obligatoria para efectuar el cambio de estado.  
11. **Extensiones:** El resumen queda disponible en modo lectura para el historial del estudiante.

## CU-TUT-07 — Cancelar Sesión del Estudiante (HU-029)

1. **ID:** CU-TUT-07  
2. **Actor:** Tutor autenticado y aprobado; Estudiante como actor pasivo (receptor).  
3. **Propósito:** Anular una sesión activa liberando el bloque en la agenda.  
4. **Resumen:** El tutor cancela la sesión; el sistema libera la disponibilidad y dispara una notificación al estudiante.  
5. **Precondiciones:** JWT válido; sesión en estado `PENDING`.  
6. **Flujo normal:** (1) selecciona la sesión a cancelar, (2) confirma la alerta, (3) `PUT /api/sessions/{id}/cancel`, (4) el sistema cambia el estado de la cita, (5) *<<include>>* dispara un correo SMTP vía Mailtrap al estudiante, (6) libera el bloque horario, (7) responde 200 OK.  
7. **Alternativas:** Puede abortar la acción en el paso de confirmación en el frontend.  
8. **Excepciones:** Si el servicio de Mailtrap falla o da timeout, la API registra el error (log) pero retorna 200 OK y efectúa la cancelación para no corromper la agenda.  
9. **Postcondiciones:** `sessions.status = CANCELLED_BY_TUTOR`. El espacio queda disponible inmediatamente para otros estudiantes.  
10. **Reglas:** El correo disparado debe incluir obligatoriamente: fecha, hora original, materia y nombre del tutor.  
11. **Extensiones:** Esta liberación de horario interactúa directamente previniendo conflictos en CU-TUT-04.
