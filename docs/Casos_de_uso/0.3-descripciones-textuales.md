# Descripciones textuales de casos de uso 

## MÓDULO A — Identidad y autenticación 

## CU-EST-01 — Registrarse como estudiante (HU-001)

1. **ID:** CU-EST-01  
2. **Actor:** Estudiante no registrado.  
3. **Propósito:** Crear una cuenta para acceder a tutorías.  
4. **Resumen:** El estudiante completa nombre, apellido, carnet, email, contraseña y envía la solicitud.  
5. **Precondiciones:** Email y carnet no existen; la API y MySQL están disponibles.  
6. **Flujo normal:** (1) abre `/registro`, (2) ingresa datos y contraseña (validación en tiempo real), (3) cliente valida formato, (4) `POST /api/auth/register/student` envía datos, (5) backend valida contraseña (8+ chars, mayúscula, minúscula, número), (6) encripta con bcrypt, (7) inserta en `users` y `student_profiles`, (8) responde con estado PENDING.  
7. **Alternativas:** Puede ir a login si ya tiene cuenta.  
8. **Excepciones:** Email inválido, carnet duplicado, contraseña débil, campos faltantes → 400 o 409 con mensaje específico.  
9. **Postcondiciones:** `users.status = PENDING`, perfil creado, contraseña nunca visible en claro. Estudiante ve página de éxito.  
10. **Reglas:** Contraseña mínimo 8 caracteres con mayúscula, minúscula y número; carnet único; email único.  
11. **Extensiones:** CU-ADM-01 puede aprobar la solicitud (HU-004).



## CU-EST-02 — Iniciar sesión como estudiante (HU-006)

1. **ID:** CU-EST-02  
2. **Actor:** Estudiante registrado.  
3. **Propósito:** Acceder a tutorías, agendar sesiones y consultar perfil.  
4. **Resumen:** El estudiante ingresa email y contraseña; backend valida estado y emite JWT.  
5. **Precondiciones:** Perfil existe y fue aprobado (`APPROVED`).  
6. **Flujo normal:** 
    - abre `/login/student`
    - ingresa email y contraseña
    - `POST /api/auth/login/student` consulta usuario
    - valida `status=APPROVED`
    - compara contraseña con bcrypt
    - si coinciden, emite JWT con `{ id, studentId, role: "student", email, status }`
    - cliente guarda token en localStorage
    - redirige a `/dashboard/student`.  
7. **Alternativas:** Si no tiene cuenta, enlace a `/registro`.  
8. **Excepciones:** Credenciales inválidas → 401; estado `PENDING|REJECTED|DISABLED` → 403 con mensaje "Cuenta no aprobada".  
9. **Postcondiciones:** Token en localStorage, sesión activa por 24 horas.  
10. **Reglas:** Solo estudiantes `APPROVED` pueden loguearse; JWT contiene studentId para operaciones posteriores.  
11. **Extensiones:** JWT habilita HU-012 (agendar), HU-013 (ver sesiones), HU-020 (historial).



## CU-ADM-01 — Iniciar sesión de administrador 2FA (HU-003)

1. **ID:** CU-ADM-01  
2. **Actor:** Administrador.  
3. **Propósito:** Acceder al panel administrativo con máxima seguridad.  
4. **Resumen:** Requiere dos factores: email + contraseña, luego validación de archivo.  
5. **Precondiciones:** Cuenta admin existe en `users` con `role=admin`; archivo `auth2-ayd1.txt` es conocido.  
6. **Flujo normal (Fase 1):** (1) abre `/login/admin`, (2) ingresa email y contraseña, (3) `POST /api/auth/login/admin` consulta usuario, (4) valida rol=admin, (5) compara contraseña con bcrypt, (6) si OK, responde `{ phase: 1, adminId, email }` (SIN JWT), (7) redirige a `/login/admin/2fa`.  
7. **Flujo normal (Fase 2):** (1) sube archivo `auth2-ayd1.txt`, (2) `POST /api/auth/login/admin/2fa` valida nombre exacto, (3) lee contenido (hash bcrypt), (4) compara con hash almacenado, (5) si OK, emite JWT con `{ id, role: "admin", email, status }`, (6) cliente guarda token, (7) redirige a `/admin/dashboard`.  
8. **Excepciones (Fase 1):** Credenciales inválidas → 401. (Fase 2): archivo inválido, nombre incorrecto, hash no coincide → 400 o 401.  
9. **Postcondiciones:** JWT generado; admin accede a rutas protegidas por 8 horas.  
10. **Reglas:** Sin Fase 2, NO hay JWT. La contraseña del archivo 2FA es diferente a la del login inicial. Archivo obligatorio.  
11. **Extensiones:** JWT habilita HU-004 (aprobar), HU-005 (rechazar), HU-024 (gestionar usuarios).


## CU-ADM-02 — Verificar acceso de administrador (HU-003 T-003.3)

1. **ID:** CU-ADM-02  
2. **Actor:** Admin autenticado.  
3. **Propósito:** Confirmar que el admin tiene sesión válida.  
4. **Resumen:** Ruta protegida que requiere JWT válido y rol admin.  
5. **Precondiciones:** JWT en localStorage; token no expirado.  
6. **Flujo normal:** (1) cliente envía `GET /api/auth/admin/profile` con `Authorization: Bearer <token>`, (2) middleware `authenticateJWT` valida firma y expiración, (3) middleware `authorizeAdmin` verifica `role=admin`, (4) controlador responde con datos públicos del admin, (5) frontend muestra página de bienvenida.  
7. **Alternativas:** Si token expiró, cliente puede re-loguearse.  
8. **Excepciones:** Sin token → 401; token inválido → 401; rol ≠ admin → 403; token expirado → 401.  
9. **Postcondiciones:** Admin mantiene sesión activa.  
10. **Reglas:** JWT debe ser presentado en header `Authorization: Bearer ...`; solo rol `admin` autorizado.  
11. **Extensiones:** Acceso a todas las rutas administrativas (HU-004, HU-005, etc.).



## Módulo B (Tutor)

### CU-TUT-01 — Registrarse como tutor (HU-002)

1. **ID:** CU-TUT-01  
2. **Actor:** Tutor no registrado; Administrador como actor secundario de aprobación.  
3. **Propósito:** Solicitar una cuenta para ofrecer tutorías.  
4. **Resumen:** El tutor completa datos personales/profesionales, adjunta fotografía y envía la solicitud.  
5. **Precondiciones:** Correo, carnet e identificación no existen; la API y MySQL están disponibles.  
6. **Flujo normal:** (1) abre registro, (2) ingresa datos y contraseña, (3) adjunta JPG/PNG/WEBP de hasta 5 MB, (4) el sistema valida, hashea con bcrypt, guarda perfil y asocia la materia, (5) responde solicitud pendiente.  
7. **Alternativas:** Puede seleccionar `OTHER` o `UNSPECIFIED` en género; el catálogo reutiliza una materia existente con el mismo nombre.  
8. **Excepciones:** Campos faltantes, correo inválido, contraseña débil, fecha/año inválidos, foto ausente o duplicados devuelven 400/409 y limpian el archivo temporal.  
9. **Postcondiciones:** `users.status = PENDING`, perfil creado y contraseña nunca visible en claro.  
10. **Reglas:** Foto obligatoria; contraseña de mínimo 8 caracteres con mayúscula, minúscula y número.  
11. **Extensiones:** CU-ADM-02 puede aprobar o rechazar la solicitud.

### CU-TUT-02 — Iniciar sesión como tutor (HU-007)

1. **ID:** CU-TUT-02  
2. **Actor:** Tutor registrado.  
3. **Propósito:** Acceder a horarios, perfil y sesiones.  
4. **Resumen:** La API compara correo/contraseña y verifica el estado administrativo.  
5. **Precondiciones:** Existe perfil tutor asociado; la cuenta fue aprobada.  
6. **Flujo normal:** (1) ingresa correo y contraseña, (2) backend consulta rol tutor, (3) compara bcrypt, (4) verifica `APPROVED`, (5) emite JWT de 8 horas.  
7. **Alternativas:** El enlace “Regístrate como tutor” lleva a `/register`.  
8. **Excepciones:** Datos incorrectos → 401; `PENDING`, `REJECTED` o `DISABLED` → 403 con mensaje específico.  
9. **Postcondiciones:** Token guardado por el cliente y enviado como Bearer en rutas privadas.  
10. **Reglas:** No se permite acceso por conocer únicamente el correo; el rol debe ser `tutor`.  
11. **Extensiones:** El JWT habilita CU-TUT-03, CU-TUT-04 y CU-TUT-05.

### CU-TUT-03 — Establecer disponibilidad (HU-008)

1. **ID:** CU-TUT-03  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Publicar los días y horas en que atiende.  
4. **Resumen:** Selecciona uno o más días y un rango común de inicio/fin.  
5. **Precondiciones:** JWT válido con `role=tutor`; perfil existente.  
6. **Flujo normal:** (1) marca días, (2) define horas, (3) cliente valida, (4) `POST /api/tutors/me/schedules` reemplaza la disponibilidad activa en una transacción, (5) confirma guardado.  
7. **Alternativas:** Puede consultar el horario actual con `GET /api/tutors/me/schedules`.  
8. **Excepciones:** Ningún día, hora inválida o inicio mayor/igual al fin → 400.  
9. **Postcondiciones:** Cada día queda asociado al mismo rango en `schedules` y puede consultarse públicamente.  
10. **Reglas:** Días ISO 1–7; `start_time < end_time`; máximo una fila activa por tutor y día.  
11. **Extensiones:** CU-TUT-04 permite modificar posteriormente el horario.

### CU-TUT-04 — Actualizar disponibilidad (HU-019)

1. **ID:** CU-TUT-04  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Adaptar días y rango sin dejar sesiones pendientes fuera de agenda.  
4. **Resumen:** El tutor edita el formulario y el backend verifica conflictos antes de guardar.  
5. **Precondiciones:** Horario existente, JWT válido y sesiones `PENDING` consultables.  
6. **Flujo normal:** (1) carga horario, (2) modifica días/rango, (3) `PUT /api/tutors/me/schedules` bloquea filas, (4) comprueba cada sesión pendiente, (5) actualiza filas y confirma.  
7. **Alternativas:** Si no hay conflictos se reemplazan días y se conservan las sesiones.  
8. **Excepciones:** Una sesión cae en día no seleccionado o fuera del rango → 409 y rollback completo.  
9. **Postcondiciones:** Horario actualizado o sin cambios si hubo conflicto.  
10. **Reglas:** La comparación de intervalos es inclusiva por contención: la sesión debe quedar dentro del rango nuevo.  
11. **Extensiones:** HU-014 consume las sesiones pendientes que protegen esta actualización.

### CU-TUT-05 — Consultar y actualizar perfil (HU-023)

1. **ID:** CU-TUT-05  
2. **Actor:** Tutor autenticado y aprobado.  
3. **Propósito:** Mantener vigente la información personal y profesional.  
4. **Resumen:** Consulta su perfil y modifica datos salvo el correo.  
5. **Precondiciones:** JWT válido y perfil asociado.  
6. **Flujo normal:** (1) `GET /api/tutors/me/profile`, (2) muestra correo de solo lectura, (3) edita campos permitidos, (4) `PUT` valida y guarda, (5) confirma actualización.  
7. **Alternativas:** Puede enviar una nueva contraseña opcional; se valida y almacena con bcrypt.  
8. **Excepciones:** Intento de cambiar correo → 400; contraseña débil → 400; carnet/identificación duplicados → 409.  
9. **Postcondiciones:** Perfil actualizado; correo y contraseña mantienen sus reglas de seguridad.  
10. **Reglas:** Todos los datos del perfil son obligatorios; el correo es inmutable.  
11. **Extensiones:** El cambio se refleja en el listado público de tutores aprobados.


## MÓDULO C: Administración de usuarios

## CU-ADM-03 — Aprobar o rechazar registro de estudiante (HU-004)

1. **ID:** CU-ADM-03  
2. **Actor:** Admin autenticado.  
3. **Propósito:** Gestionar solicitudes de registro de estudiantes.  
4. **Resumen:** Admin visualiza tabla de estudiantes `PENDING` y aprueba o rechaza cada uno.  
5. **Precondiciones:** JWT válido con `role=admin`; existen estudiantes en estado `PENDING`.  
6. **Flujo normal (Aprobar):** (1) admin ve tabla de solicitudes, (2) selecciona estudiante, (3) hace clic en "Aprobar", (4) `PUT /api/users/:id/approve` cambia `status=APPROVED`, (5) envía correo via Mailtrap (HU-004 extensión), (6) tabla actualiza.  
7. **Flujo normal (Rechazar):** (1) admin selecciona estudiante, (2) hace clic en "Rechazar", (3) `PUT /api/users/:id/reject` cambia `status=REJECTED`, (4) envía correo con motivo, (5) tabla actualiza.  
8. **Excepciones:** Usuario no existe → 404; usuario ya aprobado → 409; error en correo → 500 (pero status cambia igual).  
9. **Postcondiciones:** Usuario en estado `APPROVED` o `REJECTED`; correo enviado; estudiante puede loguearse solo si `APPROVED`.  
10. **Reglas:** Admin no puede aprobar/rechazar nuevamente un usuario ya procesado; correo es asincrónico.  
11. **Extensiones:** Notificación por Mailtrap (HU-004).


## CU-ADM-04 — Aprobar o rechazar registro de tutor (HU-005)

1. **ID:** CU-ADM-04  
2. **Actor:** Admin autenticado.  
3. **Propósito:** Gestionar solicitudes de registro de tutores.  
4. **Resumen:** Admin visualiza tabla de tutores `PENDING` y aprueba o rechaza.  
5. **Precondiciones:** JWT válido; tutores en estado `PENDING` existen.  
6. **Flujo normal:** Similar a CU-ADM-03, pero para tabla `tutor_profiles`. (1) tabla de solicitudes, (2) selecciona tutor, (3) "Aprobar" o "Rechazar", (4) `PUT /api/users/:id/approve|reject`, (5) correo enviado, (6) tutor puede loguearse si `APPROVED`.  
7. **Excepciones:** Similar a CU-ADM-03.  
8. **Postcondiciones:** Tutor en estado `APPROVED` o `REJECTED`; notificación enviada.  
9. **Reglas:** Una solicitud no puede procesarse dos veces.  
10. **Reglas:** Correo es informativo; no bloquea transacción.  
11. **Extensiones:** Notificación por Mailtrap (HU-005).



## CU-ADM-05 — Administrar estudiantes aprobados (HU-024)

1. **ID:** CU-ADM-05  
2. **Actor:** Admin autenticado.  
3. **Propósito:** Consultar, visualizar y desactivar estudiantes aprobados.  
4. **Resumen:** Admin ve tabla de estudiantes `APPROVED` y puede desactivarlos (dar de baja lógica).  
5. **Precondiciones:** JWT válido; estudiantes `APPROVED` existen.  
6. **Flujo normal:** (1) admin abre "Gestión de Estudiantes", (2) ve tabla con nombre, carnet, email, status, (3) selecciona estudiante, (4) opción "Dar de baja", (5) `PUT /api/users/:id/disable` cambia `status=DISABLED`, (6) estudiante NO puede loguearse, (7) tabla actualiza.  
7. **Alternativas:** Admin puede buscar por carnet o email.  
8. **Excepciones:** Usuario no existe → 404; usuario ya `DISABLED` → 409.  
9. **Postcondiciones:** Estudiante con `status=DISABLED`; intentos de login rechazados con 403.  
10. **Reglas:** Desactivación es lógica, no física (datos persisten); `DISABLED` es estado final sin reactivación en Sprint 1.  
11. **Extensiones:** Reporte de estudiantes (HU-026).



## CU-ADM-06 — Administrar tutores aprobados (HU-025)

1. **ID:** CU-ADM-06  
2. **Actor:** Admin autenticado.  
3. **Propósito:** Consultar, visualizar y desactivar tutores aprobados.  
4. **Resumen:** Similar a CU-ADM-05, pero para tutores.  
5. **Precondiciones:** JWT válido; tutores `APPROVED` existen.  
6. **Flujo normal:** (1) tabla de tutores, (2) selecciona tutor, (3) "Dar de baja", (4) `PUT /api/users/:id/disable`, (5) tutor NO puede loguearse, (6) tabla actualiza.  
7. **Excepciones:** Similar a CU-ADM-05.  
8. **Postcondiciones:** Tutor con `status=DISABLED`.  
9. **Reglas:** Lógica de desactivación similar a estudiantes.  
10. **Reglas:** Tutor desactivado no aparece en búsquedas públicas (HU-009).  
11. **Extensiones:** Reporte de demanda (HU-027).



## CU-ADM-07 — Reporte de tutores con más estudiantes atendidos (HU-026)

1. **ID:** CU-ADM-07  
2. **Actor:** Admin autenticado.  
3. **Propósito:** Analizar qué tutores tienen mayor demanda.  
4. **Resumen:** Admin consulta ranking de tutores por cantidad de sesiones `ATTENDED`.  
5. **Precondiciones:** JWT válido; sesiones `ATTENDED` existen.  
6. **Flujo normal:** (1) admin abre "Reportes", (2) selecciona "Tutores por Demanda", (3) `GET /api/reports/tutors-demand` consulta agrupación de sesiones por tutor, (4) ordena por cantidad descendente, (5) muestra tabla y gráfico de barras.  
7. **Excepciones:** Sin sesiones completadas → tabla vacía.  
8. **Postcondiciones:** Admin visualiza ranking; puede tomar decisiones sobre carga y recompensas.  
9. **Reglas:** Solo sesiones con `status=ATTENDED` cuentan; excluyendo `CANCELLED` y `PENDING`.  
10. **Reglas:** Actualización en tiempo real (sin caché).  
11. **Extensiones:** Exportación a CSV (futuro).
